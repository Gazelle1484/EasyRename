## 概要

  Android 33 対応のファイルリネーム支援アプリとして、スマホ内部ストレージ内のファイ
  ルを対象に、CSV に定義されたリネーム候補名を読み込み、GUI 上で「元ファイル」と「リ
  ネーム先」を手動マッチングしてリネームを実行するアプリとして整理します。

  この段階では仕様固定が目的なので、実装方法やコードには踏み込みません。

  ———

  ## 機能一覧

  ### 1. ストレージ読み込み機能

  - Android スマホ内のストレージを参照する
  - ユーザーが GUI 上で対象ディレクトリを選択できる
  - 選択したディレクトリ内のファイル一覧を取得する
  - 対象は基本的に「ファイル」のみとし、サブディレクトリの扱いは未定

  ### 2. ディレクトリ選択機能

  - リネーム対象ファイルが格納されたディレクトリを選択する
  - Android 33 のストレージ制約を考慮し、ユーザー操作によるディレクトリ選択を前提と
    する
  - 選択済みディレクトリの URI またはパス相当情報を保持する

  ### 3. CSV 読み込み機能

  - リネーム先ファイル名、またはリネーム規則が記述された CSV を読み込む
  - CSV には以下のような値が含まれる想定

  A1-1_*
  A1-2_*
  A1-3_*

  - A1-1_* のように記述されている場合、* 部分に元ファイル名を反映し、先頭に A1-1_ を
    付けた名前として扱う
  - CSV の読み込み元は、スマホ内ストレージ上の CSV ファイルを想定する

  ### 4. リネーム候補生成機能

  - CSV の各行からリネーム先ファイル名候補を生成する
  - * を含む場合は、選択された元ファイル名を差し込む
  - * を含まない場合は、その文字列をそのままリネーム先候補として扱う
  - ファイル名として不正な文字が含まれる場合はエラー扱いにする

  ### 5. リネームマッチング機能

  - 画面左側にリネーム前のファイル一覧を表示する
  - 画面右側に CSV から読み込んだリネーム先候補一覧を表示する
  - 左右から 1 件ずつ選択する
  - 元ファイルとリネーム先が両方選択された場合のみ、決定ボタンを有効化する

  ### 6. リネーム実行機能

  - 選択された元ファイルを、選択されたリネーム先ファイル名に変更する
  - 実行前に以下を確認する
      - リネーム先ファイル名が空でない
      - 同名ファイルが既に存在しない
      - ファイル名に使用できない文字が含まれていない
      - 対象ファイルへの書き込み権限がある
  - 成功後はファイル一覧を更新する
  - 使用済みのリネーム候補は一覧から除外、または使用済み表示にする

  ### 7. 権限管理機能

  - Android 33 のストレージアクセス仕様に対応する
  - 必要に応じてファイルまたはディレクトリへのアクセス許可を取得する
  - ユーザーが明示的に選択したディレクトリ・CSV ファイルに対して操作する前提にする

  ### 8. エラー表示機能

  - CSV 読み込み失敗
  - ディレクトリ読み込み失敗
  - リネーム失敗
  - 権限不足
  - 同名ファイル存在
  - 不正なファイル名
  - CSV フォーマット不正

  これらを GUI 上で分かりやすく通知する。

  ———

  ## 画面一覧

  ### 1. ホーム画面

  アプリ起動後の初期画面。

  主な操作：

  - リネーム対象ディレクトリを選択
  - CSV ファイルを選択
  - リネームマッチング画面へ進む

  表示内容：

  - 選択中の対象ディレクトリ名
  - 選択中の CSV ファイル名
  - 読み込み済みファイル数
  - 読み込み済みリネーム候補数

  ### 2. ディレクトリ選択画面

  Android 標準のファイルピッカー、または Storage Access Framework を利用する想定。

  目的：

  - ユーザーがリネーム対象ディレクトリを選択する

  ### 3. CSV 選択画面

  Android 標準のファイルピッカーを利用する想定。

  目的：

  - リネーム規則が記述された CSV ファイルを選択する

  ### 4. リネームマッチング画面

  メイン機能画面。

  レイアウト：

  - 左側：リネーム前ファイル一覧
  - 右側：リネーム先ファイル名候補一覧
  - 下部または上部：決定ボタン

  操作：

  - 左のファイルを 1 件選択
  - 右のリネーム候補を 1 件選択
  - 両方選択されたら決定ボタンを有効化
  - 決定ボタン押下でリネーム実行

  表示状態：

  - 未選択
  - 選択中
  - リネーム済み
  - エラー発生

  ### 5. リネーム結果表示

  リネーム実行後に結果を表示する。

  表示内容：

  - 成功メッセージ
  - 変更前ファイル名
  - 変更後ファイル名
  - 失敗時はエラー理由

  これは専用画面ではなく、ダイアログや Snackbar でもよい。

  ## データ構造

  ### RenameTargetFile

  リネーム対象の元ファイル情報。

  RenameTargetFile
  - id: 一意識別子
  - displayName: 表示用ファイル名
  - uri: ファイルを指す URI
  - size: ファイルサイズ
  - lastModified: 更新日時
  - isSelected: 選択状態
  - isRenamed: リネーム済み状態

  ### RenameRule

  CSV から読み込んだリネーム規則。

  RenameRule
  - id: 一意識別子
  - rawPattern: CSV に記述された元の文字列
  - prefix: * より前の文字列
  - suffix: * より後の文字列
  - hasWildcard: * を含むかどうか
  - isUsed: 使用済みかどうか

  例：

  rawPattern = "A1-1_*"
  prefix = "A1-1_"
  suffix = ""
  hasWildcard = true

  ### RenameCandidate

  画面右側に表示するリネーム先候補。

  RenameCandidate
  - id: 一意識別子
  - ruleId: 元になった RenameRule の ID
  - displayName: 表示用リネーム候補
  - rawPattern: CSV の元パターン
  - isSelected: 選択状態
  - isUsed: 使用済み状態

  ### RenamePair

  ユーザーが選択したリネーム対応。

  RenamePair
  - sourceFile: RenameTargetFile
  - renameCandidate: RenameCandidate
  - resolvedNewName: 実際に適用される新ファイル名

  ### RenameResult

  リネーム実行結果。

  RenameResult
  - beforeName: 変更前ファイル名
  - afterName: 変更後ファイル名
  - success: 成功したか
  - errorMessage: 失敗理由

  ## 全体アーキテクチャ

  このアプリは、Android アプリとしては MVVM + Repository パターン を前提にするのが妥
  当です。

  ### 採用する構成

  UI 層
  - 画面表示
  - ユーザー操作受付
  - 選択状態の表示

  ViewModel 層
  - 画面状態の管理
  - 選択中ファイル・選択中候補の管理
  - 決定ボタン有効/無効の判定
  - リネーム実行指示

  Domain / UseCase 層
  - CSV 解析
  - リネーム候補生成
  - リネーム名検証
  - リネーム処理の業務ルール

  Repository / Storage 層
  - Android ストレージアクセス
  - ディレクトリ内ファイル取得
  - CSV ファイル読み込み
  - 実ファイル名変更

  ### データフロー

  ユーザーがディレクトリ選択
  → Storage 層がファイル一覧取得
  → ViewModel が画面状態として保持
  → UI にファイル一覧表示

  ユーザーが CSV 選択
  → Storage 層が CSV 内容取得
  → UseCase 層が RenameRule に変換
  → ViewModel が候補一覧として保持
  → UI にリネーム先一覧表示

  ユーザーが左右から 1 件ずつ選択
  → ViewModel が RenamePair を生成
  → UseCase 層が新ファイル名を検証
  → Storage 層がリネーム実行
  → ViewModel が結果を反映
  → UI が一覧と結果を更新

  ### この構成を選ぶ理由

  MVVM を採用する理由は、画面状態とビジネスロジックを分離しやすいからです。

  このアプリでは、単にボタンを押して処理するだけでなく、以下の状態管理が必要です。

  - 左側ファイルの選択状態
  - 右側候補の選択状態
  - 決定ボタンの有効/無効
  - リネーム済み状態
  - CSV 読み込み状態
  - エラー状態

  これらを Activity や Fragment に直接書くと、UI 処理と業務ルールが混ざりやすくなり
  ます。ViewModel に状態管理を集約することで、UI は「表示するだけ」、UseCase は「判
  断するだけ」、Storage 層は「実ファイルを操作するだけ」という責務分離ができます。

  ———

  ## 採用理由・根拠

  ### MVVM を採用する理由

  Android アプリでは画面状態の変化が多く、MVVM は Jetpack Compose や LiveData /
  StateFlow と相性がよいです。

  特にこのアプリでは、リネーム対象とリネーム候補の選択状態によって UI が変わります。
  ViewModel に状態を持たせることで、画面回転や一時的な再描画にも対応しやすくなりま
  す。

  ### Repository パターンを使う理由

  Android 33 ではストレージアクセスの制約が強いため、ファイル操作の実装詳細を UI 側
  に漏らさないことが重要です。

  Repository 層を挟むことで、将来的に以下の変更があっても影響範囲を抑えられます。

  - Storage Access Framework の利用方法変更
  - MediaStore 対応
  - CSV の保存場所変更
  - 内部ストレージ以外への対応

  ### UseCase 層を分ける理由

  リネーム候補生成やファイル名検証は、UI とは独立した業務ルールです。

  たとえば A1-1_* というルールをどう解釈するか、同名ファイルをどう扱うか、不正文字を
  どう検出するかは、画面表示とは別の責務です。UseCase に分離することで、単体テストし
  やすくなります。

  ———

  ## 代替案

  ### 代替案 1: Activity / Fragment にすべて書く構成

  小規模アプリでは実装が速いです。

  ただし、今回のアプリではストレージアクセス、CSV 解析、画面状態、リネーム処理が混在
  するため、Activity が肥大化しやすくなります。将来的に CSV ルールが増えたり、リネー
  ム前プレビュー機能を追加したりすると保守が難しくなります。

  有効になる条件：

  - 画面が 1 つだけ
  - CSV 仕様が固定で非常に単純
  - 今後の機能追加をほぼ想定しない

  ### 代替案 2: Clean Architecture を厳密に採用する構成

  Entity、UseCase、Repository Interface、DataSource などを明確に分離する方法です。

  保守性とテスト容易性は高いですが、今回のアプリ規模ではやや過剰になる可能性がありま
  す。初期開発コストが増え、クラス数も多くなります。

  有効になる条件：

  - 複数人で長期開発する
  - クラウド同期や履歴管理などを追加する
  - リネームルールが複雑化する
  - テストコードを厚く書く前提がある

  ———

  ## 不明点・前提

  ### 不明点

  - CSV の列構成は 1 列だけか、複数列を想定するか
  - A1-1_* の * には元ファイル名全体を入れるのか、拡張子を除いた名前だけを入れるのか
  - 拡張子は維持するのか、CSV 側で指定できるのか
  - サブディレクトリ内のファイルも対象にするか
  - リネーム済み候補を画面から消すか、使用済み表示にするか
  - 同名ファイルが存在する場合、自動連番を付けるか、エラーにするか
  - 複数ファイルを一括マッチングする機能が必要か
  - リネーム前に確認ダイアログを出すか
  - リネーム履歴や取り消し機能が必要か
  - 対象ファイル種別を制限するか

  ### 現時点の前提

  - CSV は 1 行 1 ルールとして扱う
  - * は元ファイル名を差し込むワイルドカードとして扱う
  - リネームは 1 件ずつ手動で実行する
  - 同名ファイルが存在する場合はエラーにする
  - Android 33 対応のため、ユーザーが明示的に選択したファイル・ディレクトリのみ操作
    対象にする
  - まずは内部ストレージ上のユーザー選択ディレクトリを対象にする
  - UI は「ディレクトリ選択 → CSV 選択 → マッチング → リネーム実行」の流れにする

  ———

  ## リスク・今後の検討点

  - Android 33 のストレージ権限仕様により、通常のファイルパス操作ではなく URI ベース
    の操作が必要になる可能性が高い
  - ディレクトリ単位のリネーム権限をどこまで保持できるかは Storage Access Framework
    の制約に依存する
  - CSV の文字コードが UTF-8 以外の場合、文字化けする可能性がある
  - ファイル名に使えない文字、拡張子の扱い、同名衝突の仕様を早めに固定する必要がある
  - * の意味を曖昧にすると、リネーム結果がユーザーの期待とずれる可能性がある
  - 将来的に一括リネームを入れる場合、現在の 1 対 1 手動マッチング設計を拡張できるよ
    うにしておく必要がある
