# STEP 2: 設計（構造決定）
目的：
- コードの骨格を決める

## 指示内容：
### アーキテクチャ（MVVMなど）
#### 全体アーキテクチャ

  このアプリは、Android アプリとしては MVVM + Repository パターン を前提にするのが妥
  当です。

  ##### 採用する構成

  UI 層
  - 画面表示
  - ユーザー操作受付
  - 選択状態の表示

  ViewModel 層
  - 画面状態の管理
  - 選択中ファイル・選択中候補の管理
  - 決定ボタン有効/無効の判定
  - リネーム実行指示

  Domain / UseCase 層
  - CSV 解析
  - リネーム候補生成
  - リネーム名検証
  - リネーム処理の業務ルール

  Repository / Storage 層
  - Android ストレージアクセス
  - ディレクトリ内ファイル取得
  - CSV ファイル読み込み
  - 実ファイル名変更

  #### データフロー

  ユーザーがディレクトリ選択
  → Storage 層がファイル一覧取得
  → ViewModel が画面状態として保持
  → UI にファイル一覧表示

  ユーザーが CSV 選択
  → Storage 層が CSV 内容取得
  → UseCase 層が RenameRule に変換
  → ViewModel が候補一覧として保持
  → UI にリネーム先一覧表示

  ユーザーが左右から 1 件ずつ選択
  → ViewModel が RenamePair を生成
  → UseCase 層が新ファイル名を検証
  → Storage 層がリネーム実行
  → ViewModel が結果を反映
  → UI が一覧と結果を更新

  #### この構成を選ぶ理由

  MVVM を採用する理由は、画面状態とビジネスロジックを分離しやすいからです。

  このアプリでは、単にボタンを押して処理するだけでなく、以下の状態管理が必要です。

  - 左側ファイルの選択状態
  - 右側候補の選択状態
  - 決定ボタンの有効/無効
  - リネーム済み状態
  - CSV 読み込み状態
  - エラー状態

  これらを Activity や Fragment に直接書くと、UI 処理と業務ルールが混ざりやすくなり
  ます。ViewModel に状態管理を集約することで、UI は「表示するだけ」、UseCase は「判
  断するだけ」、Storage 層は「実ファイルを操作するだけ」という責務分離ができます。

  ———

  ### 採用理由・根拠

  #### MVVM を採用する理由

  Android アプリでは画面状態の変化が多く、MVVM は Jetpack Compose や LiveData /
  StateFlow と相性がよいです。

  特にこのアプリでは、リネーム対象とリネーム候補の選択状態によって UI が変わります。
  ViewModel に状態を持たせることで、画面回転や一時的な再描画にも対応しやすくなりま
  す。

  #### Repository パターンを使う理由

  Android 33 ではストレージアクセスの制約が強いため、ファイル操作の実装詳細を UI 側
  に漏らさないことが重要です。

  Repository 層を挟むことで、将来的に以下の変更があっても影響範囲を抑えられます。

  - Storage Access Framework の利用方法変更
  - MediaStore 対応
  - CSV の保存場所変更
  - 内部ストレージ以外への対応

  #### UseCase 層を分ける理由

  リネーム候補生成やファイル名検証は、UI とは独立した業務ルールです。

  たとえば A1-1_* というルールをどう解釈するか、同名ファイルをどう扱うか、不正文字を
  どう検出するかは、画面表示とは別の責務です。UseCase に分離することで、単体テストし
  やすくなります。
